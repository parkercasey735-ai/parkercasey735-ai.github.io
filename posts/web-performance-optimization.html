Core Web Vitals: A Developer's Guide to Perfect Scores

Stop guessing at performance optimization. Here are the specific techniques that consistently deliver green scores across LCP, INP, and CLS — with real code examples.

After optimizing Core Web Vitals for over 200 websites in the past three years, I can tell you with certainty: most performance problems come from the same handful of issues. The fixes aren't glamorous, but they're effective. And in 2025, with Google's page experience signals playing an increasingly important role in rankings, getting these right isn't optional.

This guide covers the specific techniques I use on every project. No theory — just practical, code-level optimizations that work.

Why Core Web Vitals Matter (More Than You Think)

Let's get the business case out of the way first. Core Web Vitals aren't just a technical exercise — they directly impact your bottom line:

  • A 100ms improvement in LCP correlates with a 1.3% increase in conversion rate (Google/Deloitte study)
  • Pages with "good" CWV scores rank, on average, 24% higher than pages with "poor" scores for the same keywords
  • Users are 24% less likely to abandon a page load when CWV metrics are in the green

In 2025, Google's three Core Web Vitals metrics are:

  1. LCP (Largest Contentful Paint) — measures loading performance. Target: under 2.5 seconds.
  2. INP (Interaction to Next Paint) — replaced FID in March 2024. Measures overall responsiveness. Target: under 200 milliseconds.
  3. CLS (Cumulative Layout Shift) — measures visual stability. Target: under 0.1.

Optimizing Largest Contentful Paint (LCP)

LCP is usually the most impactful metric to optimize because it's what users notice first — how fast does the page feel like it's loaded? The LCP element is typically the largest image, video, or text block in the viewport.

Step 1: Identify Your LCP Element

Before optimizing anything, you need to know what your LCP element actually is. Open Chrome DevTools, go to the Performance tab, record a page load, and look for the "LCP" marker. Common LCP elements include:

  • Hero images or background images
  • Large heading text blocks
  • Video poster images
  • Above-the-fold product images

Step 2: Optimize Image Loading

If your LCP element is an image (it usually is), these optimizations will have the biggest impact:

<!-- Use modern formats with fallback -->
<picture>
  <source srcset="hero.avif" type="image/avif">
  <source srcset="hero.webp" type="image/webp">
  <img src="hero.jpg"
       alt="Description"
       width="1200" height="600"
       loading="eager"
       fetchpriority="high"
       decoding="async">
</picture>

Key details:

  • fetchpriority="high" tells the browser to prioritize this image over other resources
  • loading="eager" (not lazy!) for the LCP image — you want it loaded immediately
  • AVIF format reduces file size by 50-70% compared to JPEG with no visible quality loss
  • Always include explicit width and height attributes to prevent layout shift

Step 3: Preload Critical Resources

<!-- In the <head>, before stylesheets -->
<link rel="preload" as="image" href="hero.avif" type="image/avif">
<link rel="preload" as="font" href="/fonts/inter.woff2"
      type="font/woff2" crossorigin>

Common LCP Killer: Web Fonts

Custom web fonts are one of the most common causes of poor LCP. If your LCP element is a text block and you're loading custom fonts, the browser may wait for the font to download before rendering the text. Use font-display: swap in your @font-face declarations and preload your most critical font file.

Step 4: Minimize Server Response Time

Your Time to First Byte (TTFB) directly impacts LCP. If it takes 800ms for your server to respond, your LCP can never be below 800ms. Optimizations include:

  • Use a CDN for static assets and consider edge caching for HTML
  • Implement server-side caching (Redis, Varnish)
  • Optimize database queries — the #1 cause of slow TTFB in dynamic sites
  • Consider static site generation (SSG) for content that doesn't change frequently

Optimizing Interaction to Next Paint (INP)

INP replaced First Input Delay (FID) as a Core Web Vital in March 2024, and it's a much more demanding metric. While FID only measured the delay of the first interaction, INP measures the responsiveness of all interactions throughout the page lifecycle.

The most common causes of poor INP:

  1. Long JavaScript tasks — any task that blocks the main thread for more than 50ms
  2. Excessive DOM size — pages with 1,500+ DOM elements slow down every interaction
  3. Third-party scripts — analytics, chat widgets, and ad scripts are frequent offenders

Break Up Long Tasks

// Instead of one long synchronous operation:
function processLargeDataset(data) {
  // This blocks the main thread
  data.forEach(item => heavyProcessing(item));
}

// Use yielding to break it up:
async function processLargeDataset(data) {
  for (const item of data) {
    heavyProcessing(item);

    // Yield to the main thread periodically
    if (navigator.scheduling?.isInputPending()) {
      await new Promise(resolve => setTimeout(resolve, 0));
    }
  }
}

Defer Non-Critical JavaScript

<!-- Critical scripts: load normally -->
<script src="app.js" defer></script>

<!-- Non-critical: load after page is interactive -->
<script>
  window.addEventListener('load', () => {
    // Load analytics, chat widgets, etc.
    const script = document.createElement('script');
    script.src = 'analytics.js';
    document.body.appendChild(script);
  });
</script>

Fixing Cumulative Layout Shift (CLS)

CLS measures how much the page layout shifts unexpectedly during loading. It's the most frustrating metric from a user perspective — nothing is worse than clicking a button right as the page shifts and hitting the wrong element.

The fixes are straightforward:

  • Always set dimensions on images and videos: Use width and height attributes or CSS aspect-ratio
  • Reserve space for dynamic content: Ads, embeds, and lazy-loaded content should have placeholder dimensions
  • Avoid injecting content above existing content: Banners, cookie notices, and notification bars should push content down, not insert above
  • Use CSS contain property: contain: layout on components that might shift prevents them from affecting surrounding elements
/* Reserve space for images before they load */
.responsive-image {
  aspect-ratio: 16 / 9;
  width: 100%;
  background: #f0f0f0; /* placeholder color */
}

/* Prevent font-swap layout shift */
@font-face {
  font-family: 'CustomFont';
  src: url('custom.woff2') format('woff2');
  font-display: swap;
  /* Use size-adjust to match fallback metrics */
  size-adjust: 105%;
  ascent-override: 95%;
}

Tools & Testing Workflow

Here's the testing workflow I use on every project:

  1. PageSpeed Insights — for field data (real user metrics) and lab data. Always prioritize field data.
  2. Chrome DevTools Performance panel — for deep-diving into specific issues.
  3. Web Vitals Chrome Extension — for real-time CWV monitoring during development.
  4. Google Search Console — Core Web Vitals report shows site-wide performance trends.
  5. WebPageTest — for filmstrip views and waterfall analysis on different connection speeds.

"Test on real devices, on real networks. The performance you see on your MacBook Pro with fiber internet is not the performance your users experience. Test on a mid-range Android phone over a 3G connection — that's where the truth lives."

The Performance Optimization Checklist

Here's a condensed checklist you can use for any project:

  • ☐ LCP element identified and optimized (format, size, preloading)
  • ☐ Hero image uses fetchpriority="high" and loading="eager"
  • ☐ Critical fonts preloaded with font-display: swap
  • ☐ TTFB under 800ms (ideally under 200ms with CDN)
  • ☐ No JavaScript task longer than 50ms on the main thread
  • ☐ Third-party scripts deferred until after page is interactive
  • ☐ All images and videos have explicit dimensions
  • ☐ No content injected above the fold after initial load
  • ☐ CSS contain property used on dynamic components
  • ☐ Tested on mid-range mobile device with throttled connection

Performance optimization isn't a one-time project — it's an ongoing discipline. Set up real-user monitoring (RUM), track your CWV metrics over time, and build performance budgets into your CI/CD pipeline. The sites that consistently deliver fast, stable experiences are the ones that treat performance as a feature, not an afterthought.
